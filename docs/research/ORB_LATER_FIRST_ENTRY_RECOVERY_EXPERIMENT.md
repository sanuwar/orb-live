## Purpose

One material question only: on a day where the frozen `WAITED_FIRST_VALID_0950` primary produces NO TRADE, does allowing the first genuinely valid ORB setup that appears strictly after 09:50 through 10:20 ET inclusive recover meaningful trade frequency while preserving positive trade quality? The 09:51-10:20 window is frozen before any result was read; no cutoff sweep was performed or is authorized by this milestone.

## Policies Compared

- **BASELINE = `WAITED_FIRST_VALID_0950`** (unchanged): identical to M43/M44's own primary. M44's `FALLBACK_FIRST_VALID_0950` policy is deliberately NOT reused here (it classified INSUFFICIENT_EVIDENCE).
- **`LATER_FIRST_VALID_1020`** (the one experimental policy): run the exact BASELINE 09:50 decision first. If it produces a valid trade, enter it and stop -- the later scanner never runs. Only if BASELINE produces no trade: scan every completed decision minute strictly after 09:50 through 10:20 ET inclusive across the entire frozen universe, evaluating each symbol independently with fresh data at that minute (never a stale/earlier value) via the real, unmodified `SignalEngine.evaluate`. At the first minute where any symbol is valid, select exactly one (symbol-ascending tie-break on simultaneous validity) and enter it -- exactly one trade/day maximum, no ranking by RVOL/gap/breakout strength, no "best" candidate. If nothing qualifies through 10:20, no trade.

Both policies use exactly one frozen exit arm throughout: **`BE_AFTER_050R`** -- no exit-rule variant is compared here; M43 already answered the exit question.

## Implementation

`src/orb_later_first_entry_recovery_research.py` reuses M41's `early_pool`/`select_first_candidate_per_day`/`enrich_with_decision_time` and M43's own `_waited_shadow_decision` unmodified for BASELINE (evaluated exactly once per day). The later-window SEARCH deliberately stays cheap and separate from the expensive resolution path that caused M44's own runtime bottleneck: every universe symbol at every later-window minute is checked using only the real `SignalEngine.evaluate` against already-precomputed `SessionSignalInputs.window` entries (`precompute_inputs_table` computes this for every (symbol, session_date) pair regardless of whether that symbol was ever a pre-09:50 candidate) -- no bar rescan, no shadow-decision construction. Only the ONE candidate the search settles on (if any) is ever passed to `_waited_shadow_decision` for the expensive resolution -- bounded at one extra expensive call per BASELINE-no-trade day, never one per attempted symbol-minute. `index_market_bars_by_date` (M43.5) is used throughout. `src/market_data.py` (pinned) was never touched.

## A Real Bug Found and Fixed Before Finalizing

The first empirical run's `recovery_diagnostics`/`later_only_rows` top-level aggregation in the CLI omitted `session_bounds_provider` when pooling across periods -- research-calendar periods (P_MINUS_2, P_MINUS_1, P2, P3) then validated later-window trades against the wrong (production) session calendar, spuriously classifying most of them `DATA_INVALID`. This was caught by manually cross-checking `recovery_diagnostics`'s counts against `build_policy_rows`'s own row-level outcomes for P2 (8/30 "closed" via the buggy path vs the correct 30/30), fixed at the source (`recovery_diagnostics` now accepts and forwards `session_bounds_provider`; the CLI now computes diagnostics/later-only rows per period with that period's own correct provider and pools the *results*, never a single provider across periods with different calendars), covered by two new regression tests, and the report was regenerated by rerunning the CLI against the **already-computed, unaffected checkpoints** (42s, not another ~2h09m -- the underlying `day_outcomes`/SignalEngine evaluations were correct all along; only the downstream aggregation had the bug). All numbers below are from the corrected run.
